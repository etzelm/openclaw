# Notes

## Observer and attribution method

- `tools/observe-search-prepare.mjs` is loaded with `NODE_OPTIONS=--import=file://...` (set in the Gateway env, `gateway/<arm>/<run>/gateway.cmd`) and reaches the Gateway's worker threads (threads 13 and 19 in every Gateway run). It changes no OpenClaw source.
- It wraps `DatabaseSync.prototype.prepare` for SQL mentioning `memory_index_chunks_fts` or `memory_index_paths_fts`, `DatabaseSync.prototype.function` (only `openclaw_memory_*` names recorded) and the returned statement's `all/get/iterate/run` (duration by `process.hrtime.bigint`, row count only, bound values never read into output).
- Compile counting: before the first search-statement prepare on each connection the observer calls the ORIGINAL `DatabaseSync.prototype.setAuthorizer` on the instance with a counting callback that returns `constants.SQLITE_OK`. Calling the prototype method (not the repo's instance wrapper) leaves the statement cache enabled. The authorizer fires only while SQLite compiles SQL, so any callback means a compile or re-prepare happened. No application `setAuthorizer` call was observed in any run (no `app_set_authorizer` records); the chain-to-app code path is therefore untested.
- Attribution: every `prepare` and every statement run opens a counter scope; callbacks seen inside it form one *compile episode* record (`ev: episode`, `where: prepare|run`, `cb` = callbacks, `readChunks` = SQLITE_READ callbacks on table `memory_index_chunks`, `reads` = per table). A *compile* in the tables is an episode with `readChunks > 0` (the outer statement reading `memory_index_chunks`; the path statements read it 14 times per compile, the chunk_keyword statement once).
- Requests: records are bucketed by wall-clock windows (`Date.now()` in the observer vs start/end of each `gateway call` in `calls.jsonl`; same host clock, calls strictly sequential, no records fell outside any call window in the counting runs). Window includes the CLI client's own startup, which does not touch the database.
- EXPLAIN QUERY PLAN: once per distinct SQL text per process, at its first run, with the actual bound args, under a re-entrancy guard (so the EQP's own compile is not counted). Only plans are written.
- Timing-only variant (`T101_AUTH=0`): no authorizer and no EQP, so the statement runs are not perturbed. Per-request time is the sum of the `us` of search-statement runs (excludes `reconcile_count`).
- `reconcile_count` (a `derived_count` statement on thread 13) matches the table filter; it is labelled and excluded from every search number. It is prepared once per request in both arms (not part of this change).

## Surprising or limiting

- The residual AFTER episode: one episode per request on the `chunk_keyword` statement with 5 callbacks (1 SELECT, 1 FUNCTION, 3 `SQLITE_READ` on `memory_index_chunks_fts`), none on `memory_index_chunks`. It is not a recompile of the outer statement: FTS5 prepares its own sorter statement for every `ORDER BY rank` query. The control `../fts5/fts5-sorter-control.out` shows the same 5 callbacks on every run of a parameterless FTS5 `ORDER BY rank` query and none without `ORDER BY rank`. It is why the table distinguishes "episodes" from "compiles". BEFORE has 4 episodes and 147 callbacks per request, AFTER 1 episode and 5 callbacks.
- In AFTER the statements are prepared in requests 1 and 2 (4 prepares each), then served from the cache, matching the "admission on second use" description; requests 1-2 still compile (8 compiles total in AFTER). BEFORE also prepares only in requests 1 and 2 but compiles on every run.
- One-shot CLI: BEFORE also shows run-time recompiles on the first and only run (the bare-binding recompile), so the CLI shows a visible difference too (cold process: 8 vs 4 compiles, 270 vs 153 callbacks), but reuse across runs is only visible via the Gateway.
- Timing effect is small: summed search-statement time ~4.05 ms (BEFORE) vs ~3.85 ms (AFTER) per request at steady state, about 5 percent; the Gateway's own latency lines (ms resolution) show 22 to 24 ms medians and cannot resolve it. The host was heavily loaded (1-minute load average 21.40 to 57.81 over the session); the timing-only runs started at load 23.72 to 30.11 (`gateway/<arm>/<run>/uptime-start.txt`). Raw per-request values are in the tables; before/t2 had a slow warm-up (first 5 requests 10 to 32 ms).
- Run conditions: every number comes from the final observer version (`tools/observe-search-prepare.mjs`); the index and status steps ran without the observer. The `gateway call` client processes are not observed. One state dir per arm is reused for the CLI and all Gateway runs; only `logging.file` was rewritten per run (`config.diff`).
- Plans: SQL texts differ between arms by design (`LIMIT +?`, `LIKE (? || '')`), so `sqlHash` differs for the changed statements; plans compared per statement in order of appearance.
